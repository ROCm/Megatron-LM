# Would bumping TransformerEngine help? — no, not for Newton-Schulz on ROCm

## Why the question came up

P11's trace put `Optimizer.step#TensorParallelMuon.step` at **21.1 % of device
time** at 4 L / EP=8 — the single largest row in the model, ahead of every GEMM.
Muon's cost is Newton-Schulz orthogonalisation: ~5 matmul iterations per 2-D
parameter per step, plus a TP all-gather. So a faster Newton-Schulz is the
highest-value optimisation lead this project has found.

## What we run today

`transformer_engine 2.12.0.dev0+40434cf6` — the ROCm fork, pinned to a commit
that predates the Newton-Schulz work. Verified rather than assumed:

    te.pytorch.newton_schulz          -> absent
    tex.newton_schulz                 -> absent
    tex.cusolvermp_ctx_create         -> absent

The Newton-Schulz actually executing is
`emerging_optimizers.orthogonalized_optimizers.muon_utils.newton_schulz_tp`,
pure PyTorch: all-gather the matrix onto every rank, orthogonalize redundantly,
slice the result back.

## What the ROCm fork has at HEAD

`ROCm/TransformerEngine@8f377e4` (2026-08-29) carries a real distributed
implementation, added in `a073ad5` "Newton-Schulz via cuSOLVERMp (#2706)":

    transformer_engine/pytorch/newton_schulz.py
    transformer_engine/pytorch/csrc/extensions/newton_schulz.cpp
    transformer_engine/common/newton_schulz/newton_schulz.cpp
    tests/pytorch/distributed/test_newton_schulz.py

`newton_schulz(x, ctx, num_iterations=5, coefficients=None)` — in-place, 2-D
fp32/bf16, **columns distributed across ranks**, driven by a `CusolverMpCtx`
built from a raw NCCL communicator pointer. Architecturally better than what we
run: no redundant all-gather, no redundant compute.

Our pin is an ancestor of HEAD, so the bump would be a straightforward
fast-forward.

## And it would deliver nothing here

Three independent gates, all of which have to be open and none of which is:

1. **`common/CMakeLists.txt:258-262`** lists `newton_schulz/newton_schulz.cpp`
   under `cuda_only_cpp_sources`, with the comment *"Sources that only apply to
   CUDA builds (removed when building for ROCm)"*. The source line itself is
   annotated `#CUDA-only`.
2. **`pytorch/__init__.py:76-81`** imports it under
   `if not _IS_HIP_EXTENSION:` — on a HIP build the symbol is never bound.
3. **It needs cuSOLVERMp.** `grep -rli "hipsolver|rocsolver"` across the whole
   fork returns nothing: there is no ROCm counterpart wired up. Even on CUDA it
   is behind `option(NVTE_WITH_CUSOLVERMP ... OFF)`.

So the file ships in the ROCm fork and is excluded from the ROCm build. Bumping
the pin costs a rebuild and delivers no Newton-Schulz on this hardware.

## What could actually be done

* **`use_syrk` on the non-TP path.** `emerging_optimizers.newton_schulz` takes
  `use_syrk` — a Triton kernel — defaulting to `False`. It is unreachable through
  `newton_schulz_tp` (no such parameter, no `**kwargs`), but K3 at TP=1 takes the
  `partition_dim is None` fallback, which calls `newton_schulz` directly. Worth
  measuring; it is a Triton kernel, and we are on Triton 3.7.1.
* **Per-head Muon changes the shape of the problem.** P9 already splits each
  attention matrix into per-head slices, so Newton-Schulz runs on many
  `[128, 7168]` matrices instead of one `[12288, 7168]`. Whether that is faster
  or slower on this part is **unmeasured** and was listed as the first thing to
  check in the P11 budget table.
* **A ROCm port of the distributed kernel** — the real fix, and not ours to make.

## What a ROCm port would take — scoped 2026-08-31

The kernel is small: **267 lines** in `common/newton_schulz/newton_schulz.cpp`
plus 46 in the PyTorch binding. Almost all of it is marshalling. The mathematics
is one call:

    cusolverMpNewtonSchulz(handle, ns_desc, n, m, dptr, 1, 1,
                           mat_desc, num_iterations, coefficients, CUDA_R_32F, ...)

surrounded by `cusolverMpCreate/Destroy`, `CreateDeviceGrid`,
`Create/DestroyMatrixDesc`, `NewtonSchulzDescriptorCreate/Destroy`,
`NewtonSchulz_bufferSize`, `BufferRegister/Deregister`, `NUMROC`, and
`ncclMemAlloc/MemFree`. So a port does **not** wrap a library —
`cusolverMpNewtonSchulz` *is* the algorithm, and porting means reimplementing a
distributed Newton-Schulz iteration.

| dependency | on ROCm 7.2.1 | verdict |
|---|---|---|
| RCCL comm pointer (`_comm_ptr`), `ncclMemAlloc/Free` | **present** — `ProcessGroupNCCL._comm_ptr` exists, `librccl.so` ships | the easy ~10 % |
| distributed dense solver (`cusolverMpNewtonSchulz` et al.) | **absent** | from-scratch reimplementation |

`libhipsolver` and `librocsolver` are installed, but their headers are
`hipsolver-dense.h` / `-sparse.h` / `-refactor.h` / `-compat.h` only: grepping the
whole include tree for `hipsolverMp|NUMROC|CreateDeviceGrid|MatrixDesc` returns
**nothing**. hipSOLVER is single-process/single-GPU; cuSOLVER**Mp** is NVIDIA's
multi-process dense stack and has no ROCm counterpart. Even if one appeared,
`cusolverMpNewtonSchulz` is a bespoke entry point a generic solver would not expose.

### And it would buy nothing at K3's parallelism

The kernel distributes a matrix's **columns across ranks** —
`cusolverMpCreateDeviceGrid(handle, comm, nprow, npcol, ...)` and
`cusolverMpNUMROC(n, nb, rank, 0, nranks)` give each rank its local column count.

**K3 runs at TP=1** (`pp8 x ep28`, `results/scaleout_93l.md`). At one rank the grid
is 1x1, `NUMROC` returns the full width, and the distributed path degenerates to a
single-GPU Newton-Schulz — the same computation `emerging_optimizers` already does
locally. The port's entire value is removing redundant work at TP>1, which K3 does
not use.

If K3 ever needs TP>1 for a memory reason, this calculation changes. On the
current plan it does not.

## Outcome — the bump happened anyway, 2026-09-01

TE was moved to `2.18.0.dev0+8f377e4` for an unrelated reason: the **CK
fused-attention backward returned NaN** at `hd192_hd128`, K3's gated-MLA shape,
which was blocking a 2.97x speedup on that operator. HEAD fixes it.

The conclusion of this note is unchanged and is now measured rather than
inferred: **Newton-Schulz is still absent on ROCm at HEAD.** No
`te.pytorch.newton_schulz`, no `CusolverMpCtx`, no `tex.cusolvermp_ctx_create`.
Bumping delivered nothing for Muon, exactly as scoped -- so the recommendation
below was right about the kernel, and right that a bump should wait for something
else to need it. Something else did.

## Recommendation

**Do not port the kernel.** (The bump itself is now done, for another reason.) Bump it when something else needs it, and re-check
`cuda_only_cpp_sources` at that point. Record: findings **A20**.
