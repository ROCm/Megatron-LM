## G39 — MXFP8 activations against MXFP4 weights

Against the dequantisation of **the same** quantised operands, which is what
tests the kernel rather than testing two quantisers against each other:

| K | N | tokens | rel-L2 |
|---|---|---|---|
| 256 | 256 | 32 | 1.649e-03 |
| 512 | 1024 | 64 | 1.649e-03 |
| **3584** | **3072** | **128** | **1.663e-03** |
| **3584** | **3072** | **1024** | **1.661e-03** |

Flat across four shapes, including K3's own routed-expert geometry, and flat in
token count. 1.66e-3 is bf16 accumulation, not format loss.

## The swizzle is not optional, and skipping it does not fail

The weight scales must go through `swizzle_scales` with
`swizzle_mx_scale="CDNA4_SCALE"`. Pass them unswizzled and the kernel does not
raise — it reads each scale from the wrong position and returns a plausible
tensor that is wrong by **rel-L2 0.53**, about half its own magnitude. It was
found by not believing a first result:

| | rel-L2 |
|---|---|
| swizzled | **1.66e-03** |
| unswizzled | **0.53** |

That 320x gap is now a test, so the fast path cannot silently lose its scales.

## G40 — the STE backward is exact, not approximate

`gradcheck` is invalid here by construction: an STE backward is deliberately not
the derivative of its forward (rule R4.4). So the gate compares against an
explicit fake-quant reference — and given the same incoming gradient, both the
input and weight gradients match at **rtol 0, atol 0**.

Getting there required fixing the easy mistake: **wgrad must be taken against the
activations that actually multiplied the weight** — the quantised ones — not the
originals. Using the originals still trains, and the gradient is quietly wrong.
The exact-equality criterion is what caught it; a tolerance would have passed.

## AITER has two MXFP4 quantisers, and they round differently

`downcast_to_mxfp` (used by the Triton MoE path) and `per_1x32_f4_quant` do not
agree on every group, though their errors are within 0.02 % of each other
(0.11843 vs 0.11866 rel-L2 on the same weights). Ours is byte-identical to
`per_1x32_f4_quant` — `QuantType.per_1x32`, the path the release serves through —
and a test asserts both facts, so "cross-checked against AITER" cannot drift to
the other entry point. MXFP8 has no such split: `downcast_to_mxfp` is
bit-identical to ours.
